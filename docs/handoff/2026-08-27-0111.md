## Problems Encountered and Decision Process

### Problem 1：DSH 是否提供可读的“当前语言” API

#### Investigation

源码检索覆盖 `packages/client/locale`、`packages/client/web`、`packages/client/runtime`、`packages/client/modules`、Host API/settings 与 Web entry。关键观察：

- Browser locale client 有明确的 `ctx.locale` service、`getSnapshot().active`/`getLocale().active`、`subscribe` 和 `zh`/`en` active id。
- activation 会维护 `document.documentElement.lang`，但这是 renderer-visible projection，不是比 `ctx.locale` 更权威的 service API。
- Host settings 读到的是可选 `locale.preference`，不能代表当前 Browser 已经依据 preference、browser detection 和 runtime state 得出的 active 值。
- HTML meta、根节点 `data-*`、boot globals 和可见 LanguageRow 文本均没有稳定 contract。

#### Solutions Considered

- **Host settings preference**：可获得持久化配置，且实现看似简单；但它可能缺失、滞后，且回答的是 preference 不是 active locale，还会把 Browser presentation 状态错误带进 Host/RPC。
- **HTML meta 或 `data-*`**：如果存在会便于 DOM 读取；但当前源码没有这些字段，依赖未声明属性会产生脆弱且不可验证的契约。
- **`navigator.language` 或设置按钮文本**：容易读取；但只能反映初始浏览器检测或人类可见 label，切换后不可靠，也可能随文案/渲染变化。
- **Browser `ctx.locale`**：有明确源码和测试证据，active 与 subscription 语义正确，能支持 live switch。

#### Final Decision

把 Browser `ctx.locale` 作为权威来源，把 `document.documentElement.lang` 作为缺失/不完整组合下的兼容 fallback；不新增语言 API。

#### Rationale

这样遵循 DSH 已有的状态所有权，满足“当前 active”语义，且实现规模最小，不重复持久化、不访问 Host 进程边界。

#### Future Implications

未来 DSH 若把 locale service 变成更严格的正式 contract，应继续优先使用 service；DOM fallback 应保留为 isolated test/load-order 保护，而不是新的主状态来源。

### Problem 2：如何保持方案简单，同时不让缺失 locale service 破坏 Client

#### Investigation

最初的直觉是把 `locale` 加入 Client 的 required `inject`。但这样在 isolated Client test、启动早期或暂时未发布 locale service 的 composition 中，组件可能在执行 fallback 前就无法 apply。review 还复现了 `ctx.get('locale')` 抛错时如果直接终止查找，就无法尝试结构化的 `ctx.locale`。

#### Solutions Considered

- **必需注入 `locale`**：类型直观，但把兼容 fallback 变成不可达路径，增加对 DSH composition timing 的耦合。
- **只读结构化 `ctx.locale`**：实现简单，但无法覆盖 Cordis public service lookup 的实际注入形态。
- **可选 `ctx.get('locale')` + 结构化 fallback + DOM fallback**：稍多一个 guarded lookup，但仍是单个 Browser module，没有新服务或依赖。

#### Final Decision

采用第三种方案；`inject` 不增加 locale，`i18n.ts` 对 lookup、snapshot/getLocale、subscription 都做 guarded access，service 不可用时静默退到 DOM/英文。

#### Rationale

兼容性被限制在一个小的 Browser seam 中，正常 DSH profile 仍使用真正的 service；缺失 capability 不会让 Runtime Inspector 整体失效，也不会发出错误的版本警告。

#### Future Implications

如果 DSH 未来正式保证 locale service 必定存在，可以简化类型声明，但不能因此删除未知/缺失 locale 的英文 fail-safe，除非产品明确改变兼容目标。

### Problem 3：复用 DSH renderer 翻译设施还是维护本地 catalog

#### Investigation

DSH 的 `SlotRegistry.installLocale()` 和 `LocaleFace.bind(ns)` 是 renderer locale infrastructure。Runtime Inspector 是同仓库外部 Bundle Client，需要同时满足独立测试、现有 artifact、自包含离线运行和不接管全局 locale 安装。

#### Solutions Considered

- **直接调用 `SlotRegistry.installLocale()`**：可复用 DSH 字典加载；但让普通 Bundle 进入 renderer 安装 seam，扩大耦合和失败面。
- **引入第三方或新的全局 i18n service**：功能完整；但对本轮几十个 Runtime Inspector 文案明显过重，并会产生第二份状态所有权。
- **在 Bundle Client 内维护 typed `zh`/`en` catalog**：代码量可控、无网络、无新依赖，且 message key 不进入 Host。

#### Final Decision

使用 `src/client/i18n.ts` 内置本地 catalog 和 translator；DSH locale service 只负责当前语言和变更通知，不负责 Runtime Inspector 字典安装。

#### Rationale

这是满足中英双语和 live switch 的最小闭环，保持 Bundle 自包含并避免改变 DSH renderer ownership。

#### Future Implications

如果将来需要大量复用 DSH 的统一文案，可重新评估正式的 namespace/LocaleFace contract；届时仍需保持 Runtime Inspector 的 Browser/Host 边界和 fallback 语义。

### Problem 4：国际化不能污染诊断数据和安全语义

#### Investigation

panel 同时渲染产品文案和技术数据。若简单对所有字符串调用翻译，可能误改用户请求、命令、路径、进程名或 Host action result；若把 locale 放进 DTO/RPC，则会扩大 Host/Browser 和 model-facing surface。

#### Solutions Considered

- **在 Host DTO/RPC 中增加 locale 或已翻译文本**：可让 Browser 变薄；但改变数据契约，把 presentation state 带进 Host，并可能污染 `port_list`。
- **翻译所有字符串**：界面表面完整；但会改变证据、用户输入和可复制的技术 identity。
- **只翻译 Client-owned copy，保留 data values 原样**：需要逐项梳理，但语义和安全边界最清楚。

#### Final Decision

locale 只存在于 Browser presentation；catalog 只包含 Runtime Inspector 自有文案。PID、port、path、executable、toolchain、Session/Call ID、request、command、FILETIME、redacted data 和 opaque Host error 均原样输出。

#### Rationale

国际化不会改变 Process origin、Verified/Inferred/Unattributed、Lifecycle owner、Managed shutdown、Direct external termination、fresh scan 或 privacy projection。

#### Future Implications

新增字段时必须先判断它是 product copy 还是 diagnostic data；只有前者可以进入 catalog。

### Problem 5：英文文案、动态状态和 live switch 的完整覆盖

#### Investigation

初始 panel 直接嵌入中文，除了 visible label，还有 placeholder、title、ARIA、empty/degraded/error、count、confirmation、action result 和固定 `zh-CN` 日期。只改标题会留下混合语言，并且可能让屏幕阅读器看到旧文案。

确定性测试与真实 Web smoke 逐步补齐：

- catalog 静态/动态行为、插值、中文 count 和英文 singular/plural。
- active service 与 DOM 冲突优先级。
- Settings live switch 后 panel 不关闭、不丢搜索和 selected listener。
- 中文 confirmation 和 localized title/ARIA。
- 英文 toolbar 的响应式宽度。

#### Solutions Considered

- **只翻译首屏主要 label**：改动少，但不满足可访问性和完整 presentation。
- **建立每个组件自己的局部翻译逻辑**：短期可写，长期会出现 key/语言状态重复。
- **共享 locale store + 单一 typed catalog + 行为测试**：一次接线后覆盖 Sidebar、panel 和 derived copy。

#### Final Decision

采用共享 store、统一 translator 和可观察行为测试；补充三处最小 CSS fit 调整以支持英文 toolbar。

#### Rationale

同一个 locale snapshot 驱动所有 UI，切换时不会产生 Sidebar/panel 分裂；测试锁定用户能观察到的双语行为，而非私有实现形状。

#### Future Implications

以后添加任何新按钮、状态或 tooltip，都必须同时补中英 key、ARIA/title 检查和至少一个对应 locale 的行为测试。

### Problem 6：review 暴露的 fallback 和测试契约问题

#### Investigation

双轴 review 发现：

- 直接依赖 `i18n.ts` 私有源代码布局的测试会阻止合理重构。
- 真实 DOM lang 应作为 supporting evidence 被断言。
- required locale inject 会破坏缺失 service fallback。
- 图标按钮缺少 localized `title` 或确认文案覆盖。
- `ctx.get('locale')` 抛错时需要继续尝试结构化 context。

#### Solutions Considered

- 保留私有源断言：反馈快，但测试与实现耦合。
- 只依赖 source literal 检查：无法证明真实双语渲染。
- 改为 public seam/observable behavior 断言，补充 service/DOM/live-switch/title/ARIA smoke：覆盖稍多，但契约稳定。

#### Final Decision

移除 private catalog/source assertions；增加 active service、DOM lang、ctx.get exception、title/ARIA、中文确认和 live switch 行为覆盖；用 `readLocaleSource` 做 guarded fallback。

#### Rationale

测试现在验证规格要求的结果，不规定 catalog 必须怎样组织；同时把 review 发现的异常路径固化为回归保护。

#### Future Implications

后续 code review 应继续优先问“用户观察到什么”，避免通过字符串计数或私有函数名替代行为测试。

## Key Decisions and Context

- DSH 的“可获取语言”结论要区分 Browser 和 Host：Browser 有 public `ctx.locale` service；当前没有适合 Runtime Inspector 的 Host/RPC current-locale API。
- active locale 的优先级为：`ctx.locale.getSnapshot().active` 或 `getLocale().active` > 已激活后的 `document.documentElement.lang` > 英文安全 fallback。`locale.preference` 只代表持久化 preference，不参与主路径。
- locale capability 必须 optional；`inject` 不要求 locale，以便在 isolated/incomplete composition 下继续使用 DOM fallback。
- 本地 catalog 只翻译 Client-owned copy；技术数据和安全语义不翻译、不改变、不回传新的 locale 字段。
- DSH locale service 是语言选择/持久化所有者；Runtime Inspector 只订阅 active state，不创建竞争设置。
- 版本号不是 i18n 的 feature gate。未知 locale/未知 DSH 版本默认 fail safe，不显示无意义兼容警告；与既有 capability-based compatibility 决策一致。
- Host 的 Process origin、Verified attribution、Inferred attribution、Unattributed、Lifecycle owner、Managed shutdown、Direct external termination、PID+creation identity fence 和 `port_list` privacy scope 均保持不变。
- 本轮最新可重复入口是 commit `228f3fd`；不要从旧 handoff 重新实现之前已经完成的 Runtime Inspector MVP。
