## Session Objectives

本阶段目标是完成 Windows Runtime Inspector MVP，并把真正的 DSH Web UI 放入同一个仓库、同一个 DSH Bundle 中，而不是拆成第二个 Web 仓库或启动独立服务。

目标范围包括：

- 在 Stock DSH 中建立可靠的 Tool Call → root PID → Windows listener/ancestry 归因链。
- 区分当前 DSH Session、其他 Session 和外部进程，并保持 PID 加 creation-time identity 的安全边界。
- 通过 DSH Job/Terminal lifecycle 关闭 managed listener；外部进程只允许经过身份复核后终止选中的单个 PID。
- 提供只读 `port_list` Tool 和 DSH Web 主界面入口、面板、搜索排序、详情复制、项目目录打开及安全操作。
- 用真实 Stock DSH 生命周期和真实 Browser-to-Host Web 路径验证，而不是只依赖单元测试。
- 评估运行时故障是否已有足够日志，便于问题定位。

## Problems Encountered and Decision Process

### Problem 1：Web UI 是否应该拆到第二个仓库

#### Investigation

产品要求是在 `dsh web` 主界面提供入口和面板，同时 Host 的进程安全边界必须保留。参考 DSH plugin 的实现方式后，确认 DSH Bundle 可以同时提供 Node Host 半和 Browser Client 半。

#### Solutions Considered

1. 第二个仓库维护 Web UI。
   - 优点：前端工程边界独立。
   - 缺点：版本、发布、测试和安全边界拆分；用户需要管理两个仓库。
2. Runtime Inspector 自己启动 companion Web server。
   - 优点：前端部署方式直观。
   - 缺点：增加端口、认证、CORS、生命周期和额外进程风险。
3. 同一仓库、同一 Bundle，同时提供 Host 和 Browser 两半。
   - 优点：一个版本、一个安装包、一套测试；符合 DSH plugin 加载模型。
   - 缺点：必须适配 DSH Client artifact、Slots 和各个认证版本的 Browser seam。

#### Final Decision

选择方案 3，记录于 `docs/adr/0004-web-client-dual-face-bundle.md`。Web 代码放在本仓库，不维护第二个 Web 仓库，也不启动独立服务。

### Problem 2：Web 入口和 Browser 构建方式

#### Final Decision

使用全局 `sidebar.footer.action` 作为入口，使用 `shell.overlay` 作为面板。入口是跨 Session 的系统级工具，不放在 conversation/composer 的局部 slot。Browser 通过 TypeScript/client bundler 生成 DSH artifact；`window.__ModuleLoader__.load` 只存在于构建产物格式，不作为业务 API。

### Problem 3：Terminal 初始 PID 为 `0`

#### Investigation

原生观察显示 node-pty/ConPTY Terminal 可能先暴露 PID `0`，在数据 readiness 后才有有效 PID。Stock DSH 当前版本仍会过早读取 PID 和 root identity。

#### Final Decision

采用精确版本、精确 shape 的 Bundle 兼容修复，并保留上游 DSH readiness 修复作为长期方向。任何未知 shape 或超时都不授予 verified attribution 或 termination authority。详见 `docs/adr/0003-delayed-terminal-pid-compatibility.md`。

### Problem 4：当前是否有足够的运行日志

#### Investigation

检查了 Host、Web bridge、Browser panel 和测试/文档。Runtime Inspector 源码没有专用 `ctx.logger`/`console` 调用。当前错误通过以下结果型信息传播：

- `runtimeInspector.health` 的兼容性和生命周期状态；
- inventory 的 `mode`、`scanComplete`、confidence、reason；
- action result 的 `status`、`reason`、`error`、`freshScan`、`portReleased`；
- Web route 的 HTTP status 和 JSON error；
- Browser 面板的 loading、incomplete、degraded、failure 和 post-action 状态。

Stock DSH 自身的 WebServer、Client Modules 和 Browser Runtime 仍有 Cordis/浏览器日志，但这些日志不能完整描述 Runtime Inspector 的扫描、归因、桥接和操作流程。

#### Current Recommendation

尚未实施代码变更，也未把日志方案写成已接受决策。建议后续增加轻量结构化日志适配层，优先写入 DSH/Cordis logger，并至少记录事件类型、状态、阶段、耗时和关联 ID；命令、argv、环境变量和敏感参数必须继续脱敏且不进入日志。是否增加有界内存诊断快照或“复制诊断信息”入口，需要在实现前单独确认。

不建议 MVP 默认创建独立持久化日志文件：它会引入日志生命周期、隐私清理和安装目录/权限问题；当前产品设计明确不持久化归因历史、不采集环境变量。

## Key Decisions and Context

- 目标是官方 Stock DSH Bundle，不修改 DSH core，不维护私有 fork。
- 只在 Windows local execution world 和明确认证版本中启用 verified attribution；不满足条件时保持 read-only degraded。
- Root observation 使用 Cordis `internal/get` non-mutating subprocess Proxy；fallback 是精确版本、可逆、fail-closed 的兼容 seam，不是 provider replacement。
- Host 是唯一可信的进程安全边界。Browser 和 `port_list` Tool 都不能获得进程句柄、scanner、registry、Job/Terminal API 或终止 primitive。
- Managed shutdown 必须经过 DSH owner API；外部操作只允许选中的单 PID，并要求最新 PID、creation identity、executable、user、protection/access 检查。
- 操作后必须 fresh scan，并明确报告端口是否释放；不能把请求成功当成端口已释放。
- command/argv 在 RPC、UI、日志和 Tool 输出前统一做脱敏和长度限制；不采集环境变量，不持久化归因历史。
- DSH 新版本必须通过原生生命周期 gate 后才能加入兼容列表；确定性单元测试不能替代真实 Stock DSH evidence。
