## Session Objectives

本轮目标是把 Runtime Inspector 从“显示所有 Windows 监听进程的技术面板”收敛为面向程序员和 vibe coder 的开发端口体验，并完成真实 DSH Web 集成：

## Problems Encountered and Decision Process

### Problem 1：来源状态和可操作性被混在一起

#### Investigation

早期状态同时表达“我们知道多少”和“用户能做什么”，导致“仅可查看”“来源未确认”和 DSH 生命周期归属互相暗示。讨论进一步确认：未找到 DSH 归因不等于证明不是 DSH。

#### Solutions Considered

- `属于 DSH / 非 DSH`：简短，但“非 DSH”证据要求过高，会把 unattributed 误报成排除结论。
- `已验证 / 推断 / 未归因`：工程准确，但主列表产品语言过重。
- 主标签两态、详情保留证据强度，操作单独呈现：首屏简单且不牺牲 Host 内部真实性。

#### Final Decision

主标签使用“由 DSH 启动 / 启动方未确认”，详情通过说明和轻量图标区分 verified/inferred/unattributed；处理方式独立显示 managed/external/read-only。

#### Rationale

系统只陈述已经确认的事实，不替用户证明否定命题；进程操作仍由独立身份复核决定。

#### Future Implications

“系统或用户启动”不应替换未知来源；如果需要更具体的产品文案，优先考虑“未确认由 DSH 启动”。

### Problem 2：未知 DSH 版本导致整面板降级

#### Investigation

真实安装中，版本不在硬编码集合时来源追踪和处理能力被整体拒绝，即使公开运行时契约仍然存在。

#### Solutions Considered

- 精确版本 allowlist：最保守，但普通非破坏性升级会无故失效。
- 完全忽略版本：公开能力合理，但私有 Terminal shape 变化会产生风险。
- 公开能力按 capability probe，私有修复继续精确版本/形状门控。

#### Final Decision

采用第三种混合策略，且不向普通用户展示“未知版本已启用”等开发者提示。

#### Rationale

版本是诊断元数据，不是公开功能权限；真正脆弱的私有 seam 仍然 fail closed。

#### Future Implications

开发者负责新版本回归，用户不承担无意义的兼容性提示成本。

### Problem 3：外部监听错误继承当前 DSH 请求

#### Investigation

最小回归复现显示，`requestFor({})` 会回退到当前 Session 最新请求，导致 PowerShell 外部 4174 行显示 DSH 会话中启动 4173 的用户请求。

#### Solutions Considered

- 继续使用最新请求作为展示 fallback：信息丰富但会产生错误关联和隐私泄漏。
- 只要求 Session 匹配：仍可能把同 Session 的其他 Call 请求串入。
- 要求显式当前 Session，并匹配 Call ID/root Call ID/Turn。

#### Final Decision

采用精确上下文匹配；缺失或不匹配显示 `—`。

#### Rationale

展示信息必须服从来源证据，不能为了减少空状态制造虚假关联。

#### Future Implications

任何新的 Conversation 投影都应默认 fail closed，不使用 latest-request fallback。

### Problem 4：系统和桌面软件噪声压过开发端口

#### Investigation

用户打开 DSH Web 时会看到 System、Spotify、Weixin、svchost、verge-mihomo 等大量无关监听。单纯按来源筛选无法回答“这是不是我的开发服务”。

#### Solutions Considered

- 隐藏所有非 DSH 监听：会错过从终端启动的开发服务和可安全处理的外部进程。
- 按进程名白名单硬编码：扩展性差，且容易误判。
- 增加与来源/操作正交的 development presentation，按项目路径和明确工具链证据分组。

#### Final Decision

默认显示当前项目和开发环境，其他监听折叠；搜索覆盖全部监听，“全部监听”允许显式展开。

#### Rationale

提高首屏信噪比，同时不删除诊断能力，也不改变安全权威边界。

#### Future Implications

分类只能是展示提示；不得被 action authority 或 verified attribution 使用。

### Problem 5：高保真稿和实际插件不一致

#### Investigation

同尺寸截图对比发现实际插件密度更松、边框更重、verified pill 接近黑色、选中行出现双描边。最新 Logo、地址和分组已出现，因此排除旧包未安装。

#### Solutions Considered

- 继续依赖宿主所有颜色变量：与 DSH 融合更强，但语义色被品牌 token 覆盖。
- 完全重做 Modal：可能破坏已对齐的 DSH 原生结构。
- 保留 DSH Modal chrome，只固定关键语义色、边框和已批准密度参数。

#### Final Decision

采用第三种细节修正，并增加静态视觉契约测试。

#### Rationale

最小范围修复能保持原生 Modal 结构，同时消除截图中可确定的落差。

#### Future Implications

后续视觉调整应先改高保真稿，再同步受测试保护的实现参数，并在真实 DSH Web 截图中验收。

### Problem 6：入口角标启动服务后不更新

#### Investigation

入口最初只在组件挂载、Session ID 或 cwd 改变时调用一次 inventory；面板拥有独立 state，手工刷新也不会同步入口。最小检查稳定证明不存在 interval、visibility 或 Host subscription。

#### Solutions Considered

- 仅在打开面板时更新：成本低，但角标长期过期。
- 10 秒轮询：成本更低，但用户认为反馈偏慢。
- 5 秒可见页轮询，加 focus/visibility 和面板 fresh scan 共享。

#### Final Decision

采用 5 秒方案，并防止同一入口扫描重叠。

#### Rationale

最长延迟符合本地开发工具预期；页面隐藏时停止，聚焦和主动操作通常能立即同步。

#### Future Implications

如果完整 inventory 成本增长，应优先增加轻量 Host change signal 或轻量 count RPC，而不是提高轮询频率。

## Key Decisions and Context

- Process origin、development relevance、lifecycle owner 和 action kind 是不同维度；任何展示分类都不能提升操作权限。
- 主来源标签不使用“非 DSH”或“系统或用户启动”，因为 unattributed 不是排除证明。
- Browser 只使用可序列化 same-origin Host RPC；Windows scanner、Koffi、PID identity、Job/Terminal 和 termination primitive 永远留在 Host。
- 外部结束进程必须在执行前重新校验 PID、创建时间、可执行文件、用户、保护级别和监听身份；不能因来源追踪失败而自动禁用，也不能因按钮可用而推导“非 DSH”。
- DSH 版本只作为诊断信息；公开行为由 capability probe 决定。私有 delayed-Terminal repair 必须继续精确认证并对未知形状 fail closed。
- 工具链 Logo 运行时不得联网；更新脚本只接受受限 HTTPS 来源并清理 SVG。
- UI 只支持 DSH 原生浅色 Modal，不引入暗色主题，不建立独立 Web 服务或第二套 UI 仓库。
- 创建时间的 canonical FILETIME 仍用于安全身份；格式化只发生在展示层。
- 用户请求必须有显式当前 Session 和 Call/Turn 证据，不能使用“最近请求”猜测。
- 入口角标表示当前 Session 已确认监听项，不是系统全部端口或当前项目全部开发端口。
