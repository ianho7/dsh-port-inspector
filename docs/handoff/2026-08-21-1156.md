## Problems Encountered and Decision Process

### Problem 1：如何在不改官方 DSH 的情况下捕获 root PID

#### Investigation

源码调研确认：PID 在 subprocess handle 返回处已经存在，但官方插件 API 没有稳定的 provider-neutral `process-started` event。Stock DSH 的部分调用路径会绕过 Cordis `internal/get` 的可观察 lookup。

#### Solutions Considered

- **A：修改 DSH core 增加 started event**：抽象最自然、长期价值最高，但当前普通开发者不能依赖 upstream PR，无法满足安装即用。
- **B：由插件接管 PowerShell Provider**：可以直接拿 PID，但需要复制 shell、background、cancellation、terminal 语义，长期维护风险高。
- **C：运行时替换 subprocess provider**：可能影响 provider teardown；插件卸载或热重载可能终止不相关用户进程。
- **D：`internal/get` Proxy + 受 gate 保护的 local method fallback**：覆盖 pinned stock path，同时保持 pass-through、exact handle identity 和不拥有进程。

#### Final Decision

Ticket 02 已采用 D：优先观察 Cordis `internal/get`，必要时仅对经过 compatibility gate 的 `LocalSubprocessRuntime.spawn` / `spawnTerminal` 安装可逆 fallback；两条 seam 用 exact handle identity 去重。

#### Rationale

D 是当前“普通用户安装 Bundle 后可用、无需 DSH core PR、不改变原有 process lifecycle”的最小可行折中。它必须锁定 `dsh-0.1.0-rc.8`，contract/compatibility 失败时退回只读模式。

### Problem 2：如何可靠判断 listener 是否属于 root

#### Investigation

仅凭 executable、command、workdir、端口或数值 PID 会在并发同名服务和 PID reuse 时误报。Windows Toolhelp32 可以给出当前 PID/父 PID 表，`GetProcessTimes` 可以给出 creation identity；两者组合可在 root 未逃逸且权限允许时完成身份 fencing。

#### Solutions Considered

- 只按 PID 或 executable 匹配：实现简单，但不能抵抗 PID reuse/同名并发，拒绝。
- 依赖 DSH 内部 scanner helper 路径：容易绑定不稳定的内部包结构，拒绝作为插件 API。
- 自有窄 scanner boundary：使用系统 `netstat.exe` + Toolhelp32 + 已验证 identity helper，并把 native calls 注入测试。

#### Final Decision

采用自有 scanner boundary。只有 cycle-free 链路中每个 traversed process 的 creation identity 均可读，且 root PID + creation identity 唯一对应一个 origin 时才是 `verified`。缺失 identity 的唯一 root 只能 `inferred`；歧义、reuse、循环、缺失 ancestor 和 escaped chain 为 `unattributed`。

#### Future Implications

Ticket 03 只提供 listener inventory 和 attribution result；它不决定终止方式。Ticket 04/05 必须根据 lifecycle owner 或 fresh identity fence 选择安全动作。

### Problem 3：如何验证而不把环境故障误认为代码故障

#### Investigation

Bun test 在 Stock DSH smoke 的 Koffi 依赖复制处遇到 `EPERM`；Volta Node 在受限环境下也无法创建其本地目录。重新使用允许访问 `D:\project\deepseek-harness` 依赖 checkout 的 Node authoritative run 后，全部 32 个测试通过，包括真实 Bundle load/dispose 和 native scanner smoke。

#### Final Decision

把 Node authoritative suite 作为结论依据，Bun 仅作为快速单元检查；继续保留 `DSH_REPO` 可选的 Stock DSH smoke 作为生命周期 gate。遇到类似权限错误时先记录为环境失败，不修改 scanner 逻辑。

## Key Decisions and Context

- 只支持声明的 Stock DSH `dsh-0.1.0-rc.8` + Windows local world；unknown version/provider/observer contract fail closed。
- Bundle 通过官方安装机制生效，允许安装/更新/移除后重启一次；不要求用户修改 DSH source 或维护 fork。
- Runtime Inspector 是观察者，不替换 provider、不调用 provider dispose 清理用户进程、不自动请求管理员权限。
- Process origin 是当前 DSH 运行期 memory-only 数据；root 退出后保留，以便 descendant listener 仍能匹配；PID 必须和 canonical decimal FILETIME 一起使用。
- 一个 Tool Call 可以对应多个 root；origin 用 exact handle identity 去重，不能按 PID 粗暴去重。
- `verified` 是证据状态，不是“看起来像”：需要完整 Tool context、有效 PID、精确 creation identity 和完整 ancestry。`inferred` 永远不能获得 managed-owner authority。
- listener scanner 只输出当前快照；它不自动终止进程。managed target 应走 DSH Job/Terminal API，external target 只有在后续 Ticket 05 的 fresh identity fence 和用户确认后才允许动作。
- 所有 command、executable、project/workdir 输出必须继续遵守长度限制和脱敏边界，不读取环境变量、不保留 raw argv。
