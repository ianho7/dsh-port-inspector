# Runtime Inspector 会话交接（2026-08-30 15:08）

## Session Objectives

本轮目标是优化 Runtime Inspector Browser 面板的全局提示体验，并解决首次打开面板时不必要的整页加载状态：

- Compose 是可选增强能力，Docker/Compose runtime 未启动时不应显示暗示故障的全局横幅。
- 失败、拒绝、不确定结果必须使用正确的成功/警告/错误语义，复制、打开目录和停止操作异常不能再被误称为刷新失败。
- 来源追踪受限与扫描未完成只保留 Header 状态胶囊和行级解释，避免重复放大全局故障；结果截断与旧快照刷新失败仍保留全局提示。
- 复制和打开目录的轻量成功反馈应自动消失；停止结果、警告和错误应保持可见。
- Sidebar 已显示确定端口数量时，Panel 首次打开应直接复用同一上下文的完整 inventory，减少“正在读取监听端口”的白屏时间，同时后台复查。
- 将项目版本从 `0.1.0` 同步提升到 `0.1.1`，但不提交、打 Tag 或发布。

范围限定在 Browser 状态模型、文案、样式、测试与文档；Host RPC、Windows 扫描、Compose 查询、来源归因和安全操作策略均不改动。

## Completed Work

### 1. 类型化、分来源的 Notice 模型

新增 `src/client/notices.ts`：

- 定义 `NoticeTone = 'success' | 'warning' | 'error'`、`NoticeSource` 和 `PanelNotice`。
- 为 inventory、复制、打开目录、停止操作及 RPC 异常提供纯映射函数。
- completed + released 映射为 success；仍监听/未知、拒绝和目标消失映射为 warning；Bridge/RPC/真实操作失败映射为 error。
- 技术详情仅保留首个非空消息行，最大 1,024 字符；`Error` 只读取 `message`，不展示 stack。
- 操作结果携带 `listenerId` 和 `port`，目标仍选中时就近显示，目标消失或选择变化时放到详情列顶部，避免附着到新行。
- 自动消失策略只对复制/打开目录的成功反馈返回 4 秒；停止成功、所有警告、错误和 inventory 状态保持可见。

新增 `tests/client-notices.test.mjs`，覆盖严重级别、操作来源、脱离目标后的放置、自动消失范围及技术详情裁剪。

### 2. Panel 状态与反馈呈现

修改 `src/client/panel.ts`：

- `PanelState` 使用 `inventoryNotice` 与 `operationNotice`，删除无类型的 `error`、`actionResult`、`postAction`。
- 增加统一 `NoticeView`：error 使用 `role="alert"`，其余使用 `role="status"`；错误详情默认折叠在“技术详情”中。
- 首次 inventory 失败显示“无法读取监听端口”与“重试”；刷新失败保留旧快照并显示“刷新失败，当前显示上次成功结果”。
- 复制/打开目录反馈显示在详情操作区；停止反馈显示在处理区或脱离后显示于详情列顶部。
- 新同类操作、手动刷新和关闭面板会清理操作反馈。
- 自动消失计时器按 notice 对象身份检查，旧计时器不会删除更新后的反馈。
- 删除 Compose unavailable、来源追踪受限、扫描未完成三类重复全局横幅。Compose 状态仍留在 Host DTO 中用于诊断；截断和刷新中状态保留。

### 3. 首次打开 Panel 的 warm snapshot

- 真正冷启动或上下文改变时仍显示真实的首次加载状态。

## Problems Encountered and Decision Process

### Problem 1：Compose 可选能力被显示为全局故障

#### Investigation

观察到项目只要存在 Docker/Compose 文件，即使用户本次不需要启动 Docker，Browser 也会显示“Compose 运行时暂不可用”。Host 仍可完成 Windows 监听扫描，因此该状态只代表可选增强查询不可用，不代表面板故障。

#### Solutions Considered

1. 保留横幅但弱化颜色或改写文案。
   - 优点：诊断信息始终可见。
   - 缺点：仍会把可选能力放大成需要用户处理的问题。
2. 将 Compose 状态改为 Header 胶囊。
   - 优点：比横幅安静。
   - 缺点：正常情况下仍制造无必要状态噪声。
3. Browser 静默跳过，Host 保留 `composeStatus` 供诊断。
   - 优点：符合 Compose 可选增强定位，不影响诊断数据和 Host 行为。
   - 风险：普通用户不会直接看到 Compose 查询失败原因。

#### Final Decision

采用方案 3。

#### Rationale

监听 inventory 仍完整可用时，不应把增强信息缺失呈现为系统故障。Host DTO 保持兼容，未来诊断仍可使用原状态。

#### Future Implications

如果未来 Compose 成为用户显式请求的核心能力，应在对应 Compose 功能入口内就近反馈，而不是恢复全局故障横幅。

### Problem 2：不同操作共享无类型的全局结果，严重级别失真

#### Investigation

旧状态使用 `error`、`actionResult` 和 `postAction`，复制、目录、停止及刷新错误缺乏来源信息；结果区域固定使用成功样式和对勾，导致 denied、still listening、unknown 也可能看起来像成功。RPC 异常还可能落入“刷新未完成”的文案。

#### Solutions Considered

1. 继续使用字符串，只在调用点选择不同 CSS class。
   - 优点：改动小。
   - 缺点：来源、目标与严重级别仍靠调用者隐式约定，容易再次混用。
2. 引入统一全局 Toast 系统。
   - 优点：反馈生命周期统一。
   - 缺点：超出当前范围，且停止结果需要稳定、就近呈现。
3. 引入类型化 Notice，并拆分 inventory 与 operation 状态。
   - 优点：映射可纯测试，来源、目标、语义和放置策略明确。
   - 风险：Panel 状态和渲染改动较多。

#### Final Decision

采用方案 3，并保持就近显示，不引入 Toast。

#### Rationale

这能直接修复错误文案和绿色误报，同时不改变 Host contract。操作结果携带目标身份，也解决了停止后行消失、结果附着到新选中行的问题。

#### Future Implications

新增操作必须先在 `notices.ts` 建立穷尽映射，再接入 Panel；不要重新引入无来源字符串状态。

### Problem 3：`dsh-ri-notice` 不自动消失

#### Investigation

初版计划有意规定“操作反馈不自动定时消失”，但实际体验表明复制和打开目录成功只是轻量确认，长期占据详情区没有价值；停止结果和失败信息则需要持续可见。

#### Solutions Considered

1. 所有 Notice 固定时间自动消失。
   - 优点：界面最干净。
   - 缺点：用户可能错过停止结果、警告和错误。
2. 所有 Notice 永久保留。
   - 优点：信息不会丢失。
   - 缺点：轻量成功确认累积为噪声。
3. 按 source + tone 选择性自动消失。
   - 优点：轻量成功短暂显示，高影响状态持久保留。
   - 风险：需要处理旧 timer 删除新 Notice 的竞态。

#### Final Decision

采用方案 3：复制/打开目录 success 4 秒后消失，其余持久。

#### Rationale

兼顾信息可读性与界面整洁；对象身份校验和 effect cleanup 避免异步竞态。

#### Future Implications

不要只按颜色决定生命周期；新增自动消失来源时必须增加 timer cancellation 和 stale identity 测试。

### Problem 4：Sidebar 已显示数量，Panel 仍从空状态重新读取

#### Investigation

Sidebar 的 badge refresh 已经从 Host 获取完整 inventory，却只发布数量。Panel 是独立状态，第一次打开时 `snapshot` 为空，因此必然显示“正在读取监听端口”，再重复发起相同 Host inventory。端口数量为 `0` 时尤其明显：用户已看到确定结果，弹窗却又进入未知状态。

#### Solutions Considered

1. 只把 Sidebar 的数量传给 Panel，先显示空列表。
   - 优点：实现简单。
   - 缺点：数量大于零时无法呈现行；数量为零也缺少完整 scan/truncation/mode 语义。
2. 将 inventory 持久化到 localStorage。
   - 优点：页面重载后也可 warm start。
   - 缺点：过期、隐私、schema/version 和跨 Session 投影风险更高。
3. 在 Browser 进程内共享完整 Host DTO，并用 Session ID + cwd 严格隔离，后台刷新。
   - 优点：复用已经支付的请求成本，无新持久化边界，仍保持最终一致。
   - 风险：必须防止上下文切换复用旧投影。

#### Final Decision

采用方案 3。

#### Rationale

这是最小且真实的性能优化：不伪造结果、不改 Host，也不取消后台复查。`snapshotContextKey` 和 focused test 明确保护跨会话/项目边界。

#### Future Implications

共享快照必须保持 Browser-memory-only、Host DTO bounded、上下文完全匹配。不要仅以端口数量或模糊项目名称判定可复用。

## Key Decisions and Context

- Compose 是可选增强能力；未启动不要求用户处理。
- 来源追踪受限和扫描未完成由 Header 胶囊与行级解释承担；结果截断和 stale refresh 仍是全局 inventory 状态。
- Notice 的严重级别来自真实结果，而不是 RPC 是否返回或操作按钮类型。
- inventory 与 operation 状态分离；操作异常永远使用对应操作文案。
- 技术错误采用“用户文案 + 默认折叠详情”，详情有界且不展示 stack。
- 操作反馈就近显示，不引入 Toast；目标消失时转为 detached，而不是跟随当前选择。
- 只有复制和打开目录的成功反馈自动消失；高影响结果与问题状态保持可见。
- warm snapshot 只复用同 Session ID + cwd 的完整 Host DTO，并始终后台复查。
- Browser 只使用可序列化 same-origin Host RPC，不能导入或复制 Windows 扫描、进程身份、Koffi、Job/Terminal 或终止原语。
- `0.1.1` 只完成版本源和现行文档同步；没有创建 release commit、Tag 或外部发布。
