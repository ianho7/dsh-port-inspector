## Problems Encountered and Decision Process

### Problem 1: A working Windows Terminal permanently exposed PID `0`

#### Investigation

The initial report treated PID `0` as a likely exited process. Version comparison and a native one-off probe showed a different lifecycle: node-pty initially exposed PID `0`, then exposed a real PID after ConPTY data while the Terminal remained usable.

The local latest DSH checkout at `528c682e` still constructs `LocalTerminalHandle` by immediately assigning `this.pid = terminal.pid` and immediately capturing `rootIdentity`. A native prototype against that checkout observed initial public/private PID `0`, repaired both fields to a real PID and creation identity after readiness, completed a token roundtrip, and terminated without residue.

VS Code independently handles the same node-pty boundary by waiting for the first data event before rereading an initially zero PID.

#### Solutions Considered

1. Treat PID `0` as process exit.
   - Pros: simple.
   - Cons: contradicted native evidence; permanently rejects a healthy ConPTY.
   - Risk: encodes the wrong lifecycle semantics.
2. Pin or roll DSH back to `node-pty@1.1.0`.
   - Pros: reasonable short-term upstream rc hotfix.
   - Cons: a Bundle cannot safely rewrite the host dependency tree; does not solve future readiness semantics.
3. Wait for an upstream DSH readiness fix only.
   - Pros: clean public ownership boundary.
   - Cons: blocks the current MVP and requires external coordination.
4. Replace the subprocess or Terminal provider.
   - Pros: complete control over readiness.
   - Cons: changes execution behavior and process ownership; unload could affect user processes.
5. Add an exact-version/exact-shape Bundle repair while preserving the upstream track.
   - Pros: works on unmodified Stock DSH, preserves provider/handle identity, naturally bypasses once PID is native-positive, and can fail closed.
   - Cons: depends on private fields and must be recertified per version.

#### Final Decision

Use option 5 for the current Bundle and retain option 3 as the preferred long-term DSH change. This decision is captured in ADR-0003.

#### Rationale and Future Implications

This is the narrowest no-fork solution that produces the PID plus creation identity required for safe attribution and managed ownership. Unknown shape, timeout, or exit never becomes verified. When DSH fixes readiness, the native-positive branch bypasses private inspection and the compatibility branch can be removed.

### Problem 2: `port_list` was unavailable in the real Stock DSH gate

#### Investigation

The delayed Terminal PID repair succeeded: the gate recorded four origins and a positive Terminal identity. It then failed because `ctx.tools.get('port_list', agent)` returned no Tool.

The Bundle `apply()` occurred before the Stock DSH `tools` service was published. The initial one-shot `registerPortListTool(readToolRegistry(ctx), ...)` therefore did nothing and never retried. Agent scoping was not the root cause.

#### Solutions Considered

1. Bypass the public Tool and call `projectPortList()` directly in the fixture.
   - Pros: easy test workaround.
   - Cons: would not verify real model-facing registration or Session privacy.
2. Force composition order or add speculative injection changes.
   - Pros: may make the property available earlier.
   - Cons: brittle against Bundle ordering and does not handle late service publication generally.
3. Observe Stock Cordis service publication and register once when `tools` becomes available.
   - Pros: verifies the real public Tool seam; registration remains reversible and bounded.
   - Cons: relies on a version-gated Cordis internal event.

#### Final Decision

Use option 3, with initial public lookup retained and one-time registration/disposal guards.

### Problem 3: Real Job/Terminal owners were not linked

#### Investigation

After Tool registration was fixed, Host rows still appeared as external because origins had no lifecycle owner. `beginLifecycleCapture()` accessed `ctx.jobs` before trying `ctx.get('jobs')`. Stock Cordis throws when an uninjected service property is read, so one throw aborted both Job and Terminal lookup paths.

#### Final Decision

Read each optional service in its own containment boundary: attempt the direct injected property, then independently use public `ctx.get()`. Focused Stock-style tests first failed and then passed; the native gate subsequently linked both `jobId` and `terminalSessionId`.

### Problem 4: External single-PID action failed after managed shutdowns succeeded

#### Investigation

Enhanced gate diagnostics first reported `access-denied`. A read-only Koffi probe showed `GetProcessInformation(..., 12, ...)` failed, while the actual `ProcessProtectionLevelInfo` enum value `7` succeeded and returned `0xFFFFFFFE` for an ordinary process.

After correcting that, the gate reported `current-user-unavailable`. `GetCurrentProcess()` returns the documented pseudo handle `-1`; the generic closable-handle validator rejected it before `OpenProcessToken` could run.

#### Solutions Considered

- Loosen or bypass identity checks: rejected because it would weaken the same-user/protected-process safety fence.
- Use shell commands or WMI for termination identity: rejected because it introduces a second race-prone process identity path.
- Correct the Win32 constants and pseudo-handle semantics while retaining the single opened target lease: selected.

#### Final Decision

Use enum value `7`, classify only `PROTECTION_LEVEL_NONE` as unprotected, and pass the current-process pseudo handle directly to `OpenProcessToken`. The target process handle remains strictly validated, identity-fenced, single-PID, and non-recursive.

### Problem 5: The release fixture's managed listener did not start reliably

#### Investigation

The fixture invoked Node through `cmd /c` with JSON shell quoting, which is not valid Windows command-line quoting for the intended argv. The listener never published its readiness file.

#### Final Decision

Call the subprocess provider with direct argv `[process.execPath, listenerFile, port, readyFile]`. This keeps the real DSH subprocess path while removing shell parsing from the fixture.

## Key Decisions and Context

- PID `0` from the affected Windows node-pty lifecycle means “not ready yet,” not necessarily “exited.”
- Verified attribution and termination authority still require a positive PID plus exact creation identity. The compatibility layer never invents either value.
- The Bundle repair is an exact private-shape exception, not permission for generic provider monkey-patching.
- The original DSH handle and provider remain authoritative. The repair changes only two stale identity fields before returning the same handle.
- Compatibility errors never turn a successful provider spawn into a failed Tool call; they suppress verified attribution and action authority instead.
- Upstream readiness remains the preferred architecture. A proper DSH fix should subscribe to data/exit immediately, cache early output, wait for positive PID, queue operations until ready, and include a Windows native smoke.
- `port_list` remains read-only, redacted, bounded, and Session-scoped. The release fixture must exercise the public registered Tool rather than bypassing it.
- Managed Job/Terminal shutdown always uses owner APIs and never escalates to direct PID termination after failure.
- External termination remains a separate, explicitly confirmed, identity-revalidated, same-user, non-system, non-protected, single-PID action.
- `GetCurrentProcess()` pseudo handle semantics are different from ordinary closable process handles; do not reuse the target-handle invalid-value check for it.
- `PROTECTION_LEVEL_NONE` is `0xFFFFFFFE`, not zero.
- Bundle unload removes observers, Tool registration, and local state without terminating user processes.
- Current DSH discussions reviewed during diagnosis: `#3428`, `#2045`, `#2851`, `#1856`, and `#3460`. The decisive current-state evidence was the local latest checkout and the unchanged `LocalTerminalHandle` implementation.
