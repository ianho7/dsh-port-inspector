# Runtime Inspector MVP Handoff — Ticket 05 resolved

## Session Objectives

继续完成 DSH Runtime Inspector Windows MVP 的 Ticket 05：External single-PID termination safety。

目标是让用户在明确选择并确认后关闭一个合格的同用户外部 listener，同时保持以下边界：

- managed Job/Terminal 必须继续走 DSH owner API，不得降级为直接 PID 终止；
- 外部动作必须抵抗 stale PID 和 PID reuse；
- 必须重新核验 PID、Windows FILETIME creation identity、executable、用户、保护状态和访问能力；
- 只能结束选中的单个 PID，不递归终止 process tree，不自动提权；
- 动作后必须 fresh scan，并且不能把扫描失败误报为端口已释放。

本次工作同时承接 Ticket 04 的未提交实现状态，因此交接内容包含 managed Job/Terminal lifecycle、scanner owner 字段以及 Ticket 05 external action 的整体工作区状态。

## Problems Encountered and Decision Process

### Problem: 现有代码没有 external process action seam

#### Investigation

现有实现只有只读 `WindowsListenerScanner` 和 Ticket 04 的 managed `LifecycleOwnerRegistry`。直接在 `LifecycleOwnerRegistry` 中加入 PID kill 会破坏 ADR-0002 的 managed-owner boundary，并可能把 managed shutdown failure 变成隐式 escalation。

#### Solutions Considered

1. **复用 DSH Job/Terminal API**
   - 优点：保留 DSH owner semantics。
   - 缺点：external process 没有 DSH owner，无法处理同用户手工启动的服务。
   - 风险：会伪造 lifecycle ownership。

2. **直接调用 Node `process.kill(pid)`**
   - 优点：实现简单。
   - 缺点：无法在一次稳定的 Windows process handle 上完成身份、用户、保护状态和访问检查；PID reuse 后可能重新命中不同进程；不能表达 protected/system/access denied 的安全原因。
   - 结论：拒绝。

3. **新增独立 external termination adapter + terminator**
   - 优点：与 managed action 分离；native handle 可作为身份 fence；测试可注入 deterministic adapter；默认实现可在不支持环境中 fail closed。
   - 缺点：需要维护 Koffi/Win32 binding，真实 Windows smoke 成本较高。
   - 风险：native struct/string/token binding 仍需真实 Windows 验证。

#### Final Decision

采用 `ExternalProcessAdapter` + `ExternalProcessLease` + `ExternalProcessTerminator`。调用方必须明确确认 selection；adapter 打开一个具备 query/terminate/synchronize 权限的 process handle，在该 handle 上读取并核验完整 snapshot 后才允许 `TerminateProcess`。

#### Rationale

该设计将 external action 的权限边界显式化，并保持 Ticket 04 的 owner API 与 direct process primitive 完全分离，符合 ADR-0002：只结束选中的单个 PID，不杀 process tree，不自动提权。

#### Future Implications

真实 Windows native smoke 必须验证 Koffi 的 token SID、`GetProcessInformation(ProcessProtectionLevelInfo)`、image path 和 process handle 行为。若任何一项 native 绑定不可读，行为必须继续是 read-only，而不是退回到弱身份检查。

### Problem: fresh scan 的空结果无法区分“端口释放”和“scanner 失败”

#### Investigation

原 `WindowsListenerScanner.scan()` 在 `listListeners()` 抛错时返回空数组；external action 若仅检查空数组，会把 `netstat.exe` 失败误报为端口已释放。

#### Final Decision

新增 `scanWithStatus()`，返回 `rows` 与 `complete`。external action 仅在 `complete === true` 时计算 `portReleased`；否则保持 `undefined`。

#### Rationale

这使“动作请求成功”和“端口释放已被观察到”成为两个独立结果，避免安全相关的 false positive。

## Key Decisions and Context

- MVP 仅支持 Stock DSH `dsh-0.1.0-rc.8`、Windows local execution world；未知版本/provider/observer contract 必须降级为 read-only。
- `ProcessOrigin` 的 root identity 来自真实 subprocess handle 的 PID 与 canonical decimal FILETIME，而不是命令、目录、端口或事后猜测。
- ancestry verified 需要完整、无歧义、cycle-free 的 PID + creation identity 路径；`inferred` 永远不给 managed owner 权限。
- managed target 的关闭优先级是 Job/Terminal owner API；managed kill/wait/quiescence failure 不得升级到 PID/process-tree termination。
- external target 必须经过明确选择和确认、fresh PID/creation time/executable、same-user、non-system、non-protected、termination access checks；只调用选中 PID 的 `TerminateProcess`。
- external action 与 `runtimeInspector.shutdown()` 必须在 API、结果和 UI 语义上分离；external direct termination 不是 graceful managed shutdown。
- plugin 不是 process owner；provider observer/fallback 只做可逆观察，unload/dispose 不得终止既有用户进程。
- command、argv、executable、project/workdir 继续遵守 bounded/redaction 规则；不读取环境变量或 secrets。
- Process origins 只在当前 DSH run 内 memory-only；DSH restart 清空历史。
- 当前工作区未提交 Ticket 04/05 变更；下一位工程师在提交前应先审阅全部 diff，避免把前序工作和本次 handoff 混淆。
