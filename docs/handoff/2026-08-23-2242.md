## Problems Encountered and Decision Process

### Problem 1：来源分类既要简洁，又不能把“未找到”说成“非 DSH”

#### Investigation

讨论确认：“未找到 DSH 归因”不等于“证明不是 DSH”。同时，verified/inferred/unattributed、managed/external/read-only 等内部状态若全部暴露，会制造难以扫描的多态标签体系。

#### Solutions Considered

1. 用户层直接显示“属于 DSH / 非 DSH”。优点是极简；风险是把证据缺失误写成否定结论。
2. 用户层显示完整内部证据状态。优点是严谨；缺点是产品语言技术化、首屏负担重。
3. 主标签只显示“DSH 来源已确认 / 来源未确认”，细节通过次级视觉和详情说明表达。

#### Final Decision

选择方案 3，并把来源能力整体不可用作为面板级状态单独表达。

#### Rationale

系统只陈述已确认事实，不替用户作缺少证据的否定判断；同时保持列表可扫描。

#### Future Implications

内部 inferred/unattributed 仍可用于排序、图标和详情证据，但不得重新膨胀为一套用户主标签。

### Problem 2：来源追踪与操作权限被混成一个状态

#### Investigation

旧逻辑用整体 compatibility mode 同时控制归因和 termination，导致 rc.2 被版本白名单拒绝后，DSH 与外部端口全部显示“仅可查看”。后续检查还发现 UI 横幅“来源追踪暂不可用，当前仅可查看”会覆盖 Host 已独立判定可执行的外部操作。

#### Solutions Considered

1. 继续使用整体 observing/read-only gate。实现简单，但一个能力失败会禁用无关功能。
2. 扩大版本白名单。可短期修 rc.2，但每个非破坏版本仍会重复故障。
3. 按 capability 独立启用，来源与操作正交；私有 repair 例外保持精确版本 gate。

#### Final Decision

选择方案 3。外部单 PID 操作只依赖 scanner 和执行时安全复核；managed shutdown 仍依赖 verified lifecycle owner。

#### Rationale

用户要完成的是判断和处理端口，不需要理解开发者的回归矩阵。安全性来自实际 contract 和执行时身份复核，而不是版本字符串。

#### Future Implications

新增 DSH 版本通常无需 UI 或 manifest 修改；只有私有 handle repair 需要 native gate 和显式认证。

### Problem 3：rc.2 被拒绝且版本识别可能读取错误包

#### Investigation

真实环境实际运行 Stock DSH rc.2。关键 rc.1/rc.2 artifact 保持一致，但旧 exact-version gate 先将插件整体降级。原版本读取还可能从插件模块解析到另一个全局安装包，而不是实际 CLI package。

#### Solutions Considered

1. 把 rc.2 加入整体白名单。
2. 完全忽略版本，包括私有 repair。
3. CLI package 锚定版本识别；公开能力按 contract；私有 repair 才使用认证版本。

#### Final Decision

选择方案 3，并在 native gate 证明仍需要相同 repair 后，将 rc.2加入私有 repair 认证集合。

#### Rationale

同时避免版本过严和私有 shape 盲目兼容两个相反风险。

#### Future Implications

版本信息只应出现在 health、ADR、测试矩阵和开发诊断中，不应出现在普通用户 UI。

### Problem 4：创建时间、项目和会话上下文均不可用

#### Investigation

- `134319632994565251` 是正确的 Windows FILETIME 安全身份，错误在于 UI 直接显示原始值。
- Host 根上下文不能取得 Browser 当前 Session；会话标题和 Conversation 属于 DSH Client 状态。
- compatibility 整体降级时 origins 被隐藏，项目目录因此一直缺失。
- 旧 UI 没有实现真实用户请求映射，只能显示工具命令或缺省值。

#### Solutions Considered

1. 把 Browser Conversation 整体发给 Host。上下文丰富，但扩大隐私和信任边界。
2. Host 猜测当前 Session。实现不可靠，且会把展示身份误作 authority。
3. Browser 本地订阅当前 Session/Conversation，只发送 current Session ID给 Host；Host 返回可信归因 DTO；Browser 在本地做有界、脱敏的展示映射。

#### Final Decision

选择方案 3；FILETIME 仅在 presentation boundary 格式化。

#### Rationale

Host 保持进程与归因权威，Browser 保持会话展示上下文，双方只交换完成产品所需的最小信息。

#### Future Implications

Browser Session ID永远不得参与 action authorization。会话文本映射必须保持 current-Session scoped、bounded、redacted。

### Problem 5：外部 PowerShell 行错误显示 4173 用户请求

#### Investigation

使用 `diagnosing-bugs` 建立最小回归：在当前 Session 索引 4173 请求后调用 `requestFor({})`，测试稳定返回该请求而不是 `undefined`。这排除了面板选中状态和 Host RPC 污染，定位到 Client context lookup：缺少 Session ID被当作允许当前 Session，随后又回退到 `latestRequest`。

#### Solutions Considered

1. 只在面板 `sessionVisibility` 层加条件。改动小，但底层 API 仍可被其他调用者误用。
2. 在 `requestFor` 边界强制显式 current Session，并删除无精确证据时的 latest fallback。
3. 允许外部行显示“当前页面最近请求”并加弱提示。产品语义错误且存在隐私混淆。

#### Final Decision

选择方案 2。

#### Rationale

“未提供”优于错误关联；用户请求属于 Session-private presentation data，必须 fail closed。

#### Future Implications

后续如果 DSH Conversation shape 变化导致映射失败，应显示“未提供”，不得通过最近消息、时间接近或相似文本猜测。

## Key Decisions and Context

1. 来源判断与可操作性是两个正交维度，不能合并为一个状态标签。
2. 用户来源主标签为“DSH 来源已确认 / 来源未确认”；“未找到关联”不等于“非 DSH”。
3. 来源追踪能力整体失效时可以显示能力提示，但不能据此覆盖仍安全可用的外部单 PID 操作。
4. 顶部“本会话已确认”只统计当前 DSH Session 的 verified listeners。
5. Session 显示标题；Call ID显示实际调用；用户请求必须精确关联到当前 Session 调用。
6. 外部监听的 Session、Call ID、用户请求应分别显示“未关联 DSH 会话 / 未提供 / 未提供”，不得借用当前会话文本。
7. UI 仅提供浅色/白色主题，强调紧凑、低噪音和可扫描性。
8. DSH 版本是开发诊断信息，不是产品状态；公开功能由 runtime capability 决定，不向用户显示版本提示。
9. 私有 Terminal repair 是版本策略的唯一窄例外，必须有 exact version + shape + native gate。
10. Browser 只能消费可序列化 Host RPC；不能导入 scanner、Koffi、Job/Terminal 或 Windows process primitive。
11. Browser current Session ID只用于展示/隐私，不授予来源、managed owner 或 termination authority。
12. managed shutdown 失败不得自动升级为 PID termination；外部操作只结束用户明确确认的单个 PID。
13. PID 操作前必须实时重新校验 PID、creation time、executable、same-user、protection/access 和监听身份，防止 PID reuse/TOCTOU。
14. 新进程必须在插件已加载的当前 DSH 运行周期内创建，才能获得 Process origin；插件更新后必须重启 Profile 并创建新任务。
