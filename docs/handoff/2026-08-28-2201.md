## Session Objectives

本阶段围绕一个可真实运行的 DSH 全栈开发场景，持续完善 Runtime Inspector 的证据链、展示和演示材料。目标是让开发者在 DSH 中交给 Agent 一个前后端分离项目任务时，可以同时启动并观察多个真实进程，并回答：

- 哪些 TCP listener 属于当前项目；
- 哪些 listener 能由 DSH Session、Tool Call 和生命周期 owner 可靠归因；
- 哪些 listener 只是 Docker Compose 基础设施关联，不能声称由 DSH 启动；
- 如何在 Runtime Inspector 中安全停止一个 DSH 管理的服务，并通过重新扫描确认端口释放；
- 新框架、新运行时或脚本包装启动时，如何避免依赖 npm/go 专用规则表；
- Sidebar 的 `.dsh-ri-entry-badge` 如何反映当前项目的完整运行环境，而不是只反映 DSH 直接管理的进程。

本阶段范围包括：

- 保持单仓库 DSH dual-face Bundle、Host/Browser 边界和现有公开 API 不变；
- 为 `demo/runtime-story` 提供最小 React/Vite + Go + PostgreSQL + Redis 演示；
- 建立有界的嵌套 Docker Compose 关联，显示服务、镜像、容器和 published port 证据；
- 建立经过 PID、创建时间和父进程链校验的 verified launch chain；
- 修复当前项目徽标只显示 2 而不是 4 的计数逻辑；
- 保留真实 DSH、Docker Desktop 和截图验收的未完成边界，不把确定性测试当作真实运行验收。

### 3. Verified launch chain

已实现并提交在 `cbd041c`：

- `src/windows-scanner.ts` 使用固定 PowerShell/CIM `Win32_Process` 投影读取有限的 PID、ParentProcessId、CreationDate、ExecutablePath、CommandLine；
- 输入 PID 经 stdin 传递，避免拼接用户输入；读取上限 64 PID、2 秒、256 KiB；
- 命令在读取后立即脱敏，公开命令长度上限 1,024；支持 URI credential、引号/非引号 Windows path 等既有脱敏边界；
- 对 PID、父 PID 和 creation-time 做二次校验，PID reuse、链路歧义、循环、身份读取失败均 fail closed；
- 只有 `confidence === 'verified'` 且存在可信 Process origin 时才向 Host DTO 暴露 `launchChain`；
- Browser detail 显示 root/intermediate/listener 节点，但 launch chain 不参与搜索、action、lifecycle owner、Compose 关联或复制权限；
- 采用 OS 事实链，适用于 Go、Vite、Python、Rust、Java、未知自定义可执行文件等，不引入 manifest/environment/port heuristic 作为强证据。

这解决了 `go run .` 最终监听进程显示为编译出的 `dsh-runtime-story.exe`、`npm run dev` 最终显示为 `node.exe` 的可信展示问题：入口命令和最终 executable 是不同层级事实，不能用 Logo 或穷举映射伪造为同一进程。

## Problems Encountered and Decision Process

### Problem 1：Docker Compose 监听被归类为开发环境，无法说明属于当前项目

#### Investigation

Windows Docker Desktop 通常由 `com.docker.backend.exe` 或代理进程持有宿主端口。仅看 PID、端口或 Docker Logo，无法证明 DSH 启动了该进程。早期面板因此只把 5432/6379 显示在 development environment，并显示“启动方未确认”。

实机 Docker Desktop probe 证明可以从当前 Workspace 的嵌套 Compose 文件和 Docker `compose ps --format json` 获取服务、镜像、容器 ID、published port；但这些证据证明的是“Compose 项目关联”，不是“DSH Tool Call 启动”。

#### Solutions Considered

- 仅按常见端口或镜像名推断：实现简单，但端口和镜像都可能重复，证据链不足，拒绝。
- 把 Docker Desktop backend PID 伪装成 DSH origin：视觉上满足，但违反 Process origin 和安全语义，拒绝。
- 在 Host 侧做有界 Compose 文件发现 + Docker runtime 查询，把 Compose 关联和 DSH attribution 分开：工作量适中，证据来自 Docker 自身，选择。

#### Final Decision / Rationale

采用第三种方案。Compose 行可以进入 current-project presentation，详情显示 compose file、service、image、container ID 和 port mapping，并带 Compose context logo；同时保留 unconfirmed source、read-only action 和不可停止 Docker backend 的边界。

#### Future Implications

当前 Workspace 的嵌套 Compose 文件会被有界扫描。如果一个大仓库包含多个独立 Compose 项目，可能需要后续项目筛选能力；不能通过放宽扫描上限或端口猜测解决。

### Problem 2：`go run .`/`npm run dev` 最终显示为 exe/node，且不能穷举所有框架

#### Investigation

Go 会编译临时 executable 后监听，Node 包管理器会再 spawn `node.exe`；因此最终 listener executable 不是用户输入的 launcher 命令。npm、Go 只是一个用户故事，不应建立仅服务于它们的规则表。

#### Solutions Considered

- 维护 `vite`、Go、框架和端口的关键字映射：初期看似直接，但新工具和脚本组合会不断产生遗漏，且类别推断会污染入口事实。
- 读取 manifest、环境变量、包管理器 lockfile 并递归解析脚本：覆盖面更大，但 shell 语义、环境隐私和长尾解析成本高，不适合作为 MVP 强证据。
- 读取 OS 真实进程链，使用 DSH Tool Call 的 root 和 Windows PID/creation identity 建立 verified ancestry；命令/入口只作为受信任链上的展示事实，未知工具保持通用 executable：选择。

#### Final Decision / Rationale

采用 OS process facts + DSH origin correlation。框架 Logo/类别识别仍是 presentation-only 的有限推断；它不参与 attribution、action 或 badge authority。新框架即使没有分类规则，只要属于 DSH verified ancestry，仍可显示 verified source、root-to-listener chain 和原始入口命令。

#### Future Implications

如果未来需要更具体的工具链名称，应新增独立的 presentation evidence source，而不是修改 process authority。未知/复合 shell 命令必须继续显示原始可解释文本或“未确认”，不可为了 Logo 伪造确定性。

### Problem 3：Demo `start.ps1 infrastructure` 无法连接 Docker Desktop

#### Investigation

出现过：`open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified.`，说明 Docker CLI 找不到 Docker Desktop Linux engine named pipe，而不是 Compose 文件格式问题。

#### Final Decision / Rationale

`start.ps1` 在 Compose 前执行 `docker info`，失败时明确提示启动 Docker Desktop 并等待 **Engine running**，再重试；不自动启动、切换远程 context 或修改项目文件。该处理保持环境边界透明，也避免把失败归因于 Runtime Inspector。

### Problem 4：徽标显示 2 而不是四个真实端口

#### Investigation

旧徽标只统计“当前 Session + verified” rows。Go/Vite 满足该条件，Compose Docker rows 因为启动方未确认而不满足，所以结果为 2；但当前项目的开发视图已经把经过 Compose runtime evidence 关联的 5432/6379 放入 `current-project`。

#### Solutions Considered

- 直接把所有 listener 计数：会把其他项目、未关联端口和系统 listener 混入徽标，拒绝。
- 给 Docker rows 伪造 verified source：破坏证据链，拒绝。
- 复用 Host 已计算的 `development.group === 'current-project'`：只增加项目范围内的 Compose 与 DSH 行，且不改 source/action 语义，选择。

#### Final Decision / Rationale

徽标改为 current-project count。对于 Demo，预期 8080、5173、5432、6379 共 4；对于无可用 source snapshot 的 read-only-degraded mode，仍显示 `—`，不把不完整数据显示为确定计数。

#### Future Implications

计数受当前 inventory snapshot 上限影响；超大项目或不完整扫描仍需显示不完整状态。若项目筛选功能落地，徽标应继续复用同一项目 scope，而不是另建一套端口计数规则。

### Problem 5：真实验收和确定性测试之间存在环境缺口

#### Investigation

当前确定性套件覆盖 Host/Browser 合同、Compose parsing、identity fencing、badge source contract 等；真实 Stock DSH gates 依赖外部 DSH checkout、Docker Desktop、Windows Terminal listener readiness 和 Browser fixture。

已记录的环境事实：

- rc.8/rc.1/rc.2 的部分或全部 Bundle/Web smoke 曾通过；
- Compose 实机 Docker Desktop 关联已通过；
- G1-G6 release fixture 曾两次看到有效 Terminal PID，但端口未进入 LISTENING，不能宣称 G4/G6 完成；
- 最近一次 Compose Web smoke 因 Stock DSH `/dsh` announcement 在 30 秒内未出现而超时，未产生新的 UI 证据；
- 某次临时 Profile 缺少 host plugin package，属于环境阻塞，不是产品证据。

#### Final Decision / Rationale

保留 fail-closed 实现和精确的环境缺口记录。不为了让测试通过而降低 Terminal/Compose/attribution 安全门槛，不把静态测试或已有历史 smoke 结果冒充本次新功能的实时截图证据。

## Key Decisions and Context

- **证据优先级**：OS PID/creation identity/parent chain 与 DSH Tool Call root 是强证据；Compose service/image/container/port 是项目基础设施关联证据；Logo、端口约定和类别名称只用于 presentation，不能赋予 source/action authority。
- **两个正交语义轴**：`Process origin`/`confidence`/`sessionVisibility` 回答“谁启动/能否确认”；`development.group`/`toolchain`/Compose evidence 回答“与哪个开发项目相关、如何展示”。任何一个轴都不能替代另一个轴。
- **当前项目徽标**：复用 Host 的 `current-project` presentation grouping，统计 DSH listener 和 Compose infrastructure；不统计所有 OS listeners，也不把计数变成权限判断。
- **Docker Logo 语义**：已知镜像显示 PostgreSQL/Redis 等产品 Logo，并可叠加 Docker Compose context；Logo 仅帮助确认 image/service，不表示 DSH 启动或 Docker PID 可控。未知镜像回退 Docker Logo。
- **Workspace 与嵌套文件**：Compose reader 以当前 DSH Workspace 为根做有界嵌套发现；`node_modules` 等生成目录跳过。极端大仓库的完整发现不是 MVP 目标，不能无限扩大深度/候选数。
- **命令链语义**：最终 listener executable 与入口命令可以不同；展示入口需要来自 verified chain，但不通过维护无限的 npm/go/framework 映射来决定归因。链只作为 detail evidence，不改变 action/search。
- **兼容性策略**：公共能力按 runtime capability probe 启用，版本只供诊断；私有 delayed-Terminal PID repair 仍按已认证的精确版本和 shape 控制。新 DSH 版本不能因为未知版本自动进入全局 degraded。
- **安全与隐私**：不采集环境变量和 secrets；命令/路径脱敏且有界；终止前后都需要 PID + creation identity 复核；Host 失败按能力独立降级；Browser 不加载其他 Session conversation。
- **工作树纪律**：下次会话从 `334805f` 开始，保留未提交的 Demo、glossary、Logo 和 project/session spec；不要 `git reset --hard`、`git clean` 或整目录 stage。
