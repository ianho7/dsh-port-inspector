## Session Objectives

本轮对话围绕 DSH Runtime Inspector 的实际 Web 使用闭环展开，目标是：

1. 让 Web 代码继续放在本仓库，并作为同一个 DSH Bundle 的 Browser/Host 双半实现。
2. 修复用户实际验证中“复制详情”只显示成功但没有写入剪贴板的问题。
3. 修复“打开项目目录”始终提示“项目目录不可用”的问题。
4. 修复新会话中 `port_list` 工具的无效 JSON Schema 错误。
5. 定位真实 `pnpm dsh web` 启动时出现 `compatibility-degraded`、进程显示 `unattributed` 的原因。
6. 重新构建、打包、安装插件，完成真实 DSH Web 验证，直到用户确认可用。

范围限定为 Windows Stock DSH Web；不修改 DSH core，不维护第二个 Web 仓库，不启动独立 HTTP 服务，不放宽进程归因或终止的安全门禁。

### 3. 修复 `port_list` JSON Schema

修改：

- `src/port-list.ts`
- `tests/port-list.test.mjs`

原问题是工具声明了 `parameters: {}`。DSH/模型提供方将其视为没有 JSON Schema 根类型，实际运行时报错：

```text

  "properties": {},
  "additionalProperties": false
}
```

影响：`port_list` 可被当前 DSH 模型工具链正常识别，同时仍然是无参数、只读工具。

## Problems Encountered and Decision Process

### Problem 1：Web UI 的仓库边界

#### Problem

用户明确要求 Web 相关代码放在当前项目中，不希望维护两个仓库。

#### Investigation

参考 DSH plugin 的 dual-face 实现方式后，确认一个包可以同时声明 Node Host 和 Browser Client artifact，并由 DSH Bundle 统一安装和加载。

#### Solutions Considered

1. 第二个仓库维护 Web UI。
   - 优点：前端边界独立。
   - 缺点：版本、安装、测试和安全边界拆分；用户需要维护两个仓库。
2. 插件自己启动 companion Web server。
   - 优点：前端开发模型直观。
   - 缺点：增加额外端口、认证、CORS、生命周期和进程风险。
3. 同仓库、同包、同 Bundle 的 Browser/Host 双半实现。
   - 优点：一个版本、一个安装包、一个安全边界和一套集成测试。
   - 缺点：需要适配 DSH Client artifact、Slot 和 Host RPC。

#### Final Decision

选择方案 3，沿用 `docs/adr/0004-web-client-dual-face-bundle.md`。Web 代码放在当前仓库，不建立第二个仓库，也不启动独立 HTTP 服务。

### Problem 2：“复制详情”提示成功但实际没有复制

#### Investigation

Host 的 `copy` endpoint 只负责生成脱敏文本；Browser RPC 直接返回了 `copied: false` 的 Host 结果，面板却无条件显示成功提示。因此 UI 的成功文案不代表系统剪贴板已经接受文本。

#### Solutions Considered

1. 由 Host 直接写 Windows 剪贴板。
   - 优点：Host 权限稳定。
   - 缺点：扩大 Host 平台耦合，且当前 DSH Browser UI 已有浏览器上下文。
2. Browser 使用 `navigator.clipboard.writeText`，Host 只生成脱敏文本。
   - 优点：权限边界清晰，Browser 不接触进程 primitive；可直接在真实 Web 中验证。
   - 缺点：需要浏览器权限或安全上下文；旧环境可能没有 Clipboard API。
3. 继续只显示“已生成”。
   - 优点：实现最小。
   - 缺点：无法满足用户对“复制详情”的实际预期。

#### Final Decision

选择方案 2，并添加 `execCommand('copy')` fallback。面板根据最终 copied 状态显示准确提示。

#### Future Implications

真实 Web smoke 应继续授予 clipboard 权限并验证 `navigator.clipboard.readText()`；复制内容必须继续使用 Host 已脱敏文本，不能把原始命令、环境变量或句柄交给 Browser。

### Problem 3：“打开项目目录”提示项目目录不可用

#### Investigation

最初失败发生在 `projectPathForOpen`：仅接受 `ProcessOrigin.workdir`，而降级/未归因行没有 origin。随后发现 Host 没有实际绑定 DSH 的打开路径能力，`openDirectory` 未传入可工作的 adapter。

#### Solutions Considered

1. 让 Browser 直接调用 `window.open` 或系统路径 API。
   - 优点：实现看起来简单。
   - 缺点：越过 Host 安全边界，不能可靠打开本地路径。
2. 插件自行启动文件管理器/独立进程。
   - 优点：不依赖 DSH API。
   - 缺点：引入新的进程启动和平台权限行为，不符合“不拥有进程”的边界。
3. 复用 DSH `apiProxy.host.openPath`，由 Host 执行打开；项目路径优先 origin workdir，必要时使用 scanner row project fallback。
   - 优点：复用 DSH 认证 Host 能力，路径不出 Host，兼容未归因但有扫描项目字段的行。
   - 缺点：依赖 Host capability 发布时机和可用性。

#### Final Decision

选择方案 3，并增加动态 capability probe；路径缺失或被脱敏时仍返回 `project-unavailable`。

#### Future Implications

旧 DSH Web 进程和旧 origin 不会因为新代码自动补录 workdir。验证目录功能时必须重启 Web 并新建进程；外部或跨重启进程仍可能保持未归因。

### Problem 4：`port_list` function schema 无效

#### Problem

新会话报错：

```text
Invalid schema for function 'port_list': schema must be a JSON Schema of 'type: "object"', got 'type: null'.
```

#### Investigation

DSH 工具注册本身允许任意 `Record<string, unknown>`，但后续模型提供方按 JSON Schema 校验参数。`parameters: {}` 没有根类型，因此在 provider validation 阶段失败。

#### Final Decision

使用显式 object-rooted schema，并加入回归测试。没有增加工具参数，也没有改变 `port_list` 的只读能力。

### Problem 5：credentials YAML 在不同 DSH 入口下类型不一致

#### Problem

全局 `dsh web` 曾提示 credentials 的 `version` 必须是 string；改动后通过源码入口 `pnpm dsh web` 又提示 version `"1"` 与源码期望 numeric `1` 不匹配。

#### Investigation

实际运行了两套不同 DSH 入口/安装图：Volta 全局安装的 DSH 与 `D:\project\deepseek-harness` 源码入口使用的 credentials parser 版本不同。用户最终使用的命令是：

```powershell
cd D:\project\deepseek-harness
pnpm dsh web --no-open --port 3080
```

该源码版本 `0.1.1-rc.1` 读取 numeric `version: 1`。

#### Final Decision

不在插件代码中兼容两套外部 credentials schema，也不继续修改用户 credentials 文件；固定后续验证使用仓库源码入口 `pnpm dsh`，并把全局 `dsh` 与源码 `pnpm dsh` 的差异记录为环境注意事项。

### Problem 6：真实 Web profile 显示 `compatibility-degraded` / `unattributed`

#### Investigation

用户通过 DSH Web 使用 PowerShell 和指定 workdir 创建后台 HTTP 服务后，面板显示：

```text
端口 18765 · PID 21500
unattributed · unattributed · node.exe
compatibility-degraded
```

临时健康探针读取到：

```json
{
  "mode": "read-only-degraded",
  "executionWorld": "unsupported",
  "observerContractAvailable": true,
  "detectedDshVersion": "0.1.1-rc.1",
  "reason": "execution-world-unsupported"
}
```

进一步探针确认真实 provider 后来确实是 `LocalSubprocessRuntime`，且同时存在 `spawn` 和 `spawnTerminal`。因此不是用户指定 PowerShell/workdir 的方式错误，而是插件初始化时读取 subprocess 太早：Web profile 中插件先挂载，subprocess 服务后发布；既有短重试窗口结束后状态没有恢复。

#### Solutions Considered

1. 放宽兼容性门禁，遇到未知 provider 也启用归因。
   - 优点：可能立即显示归属。
   - 缺点：破坏 fail-closed 安全原则，无法确认真实执行世界。
2. 增加更长的固定延时或无限重试。
   - 优点：改动小。
   - 缺点：依赖时序，无法确定服务何时发布；会产生不必要的 timer 和状态不确定性。
3. 监听 Cordis `internal/service` 的 `subprocess` 发布事件，发布后重新运行现有严格兼容性检查。
   - 优点：直接绑定真实服务生命周期，不放宽 provider/version/observer 门禁；卸载可撤销。
   - 缺点：依赖 `internal/service` observer contract，需要继续保持 fail closed。

#### Final Decision

选择方案 3。新增 `internal/service` listener；当 `serviceName === 'subprocess'` 时调用现有 `refresh(0)`。同时新增 TDD 回归测试，先捕获失败，再验证修复。

#### Result

重新 build、pack、安装并启动真实 Web 后，健康状态恢复为：

```text
observing / windows-local / verifiedAttributionEnabled=true
LocalSubprocessRuntime
```

用户重新创建后台任务后确认项目目录和相关功能可用。

## Key Decisions and Context

- Web 代码与 Host 代码必须位于同一仓库、同一 npm package、同一 DSH Bundle；使用 Browser/Host dual-face，不使用第二仓库。
- Web 入口使用 DSH additive Client Slot：全局 Sidebar 入口 + overlay 面板。
- Browser 只能使用同源、可序列化 Host RPC；不能接触 scanner、Process origin registry、Job/Terminal、Koffi 或 Windows process primitive。
- 项目目录打开必须通过 DSH Host path opener；Browser 不直接打开任意路径。
- 复制详情的内容必须来自 Host 脱敏结果；Browser 只负责写入剪贴板，不收集额外进程信息。
- `port_list` 始终只读、无 action capability，参数 schema 必须是合法的 JSON Schema object root。
- 兼容性 gate 失败时继续 read-only degraded；服务晚发布只触发重新检查，不改变安全条件。
- 只有当前 DSH 运行周期内由被观察的本地 subprocess 创建链，才可提供 verified attribution；旧进程、跨重启进程、未知 provider 和身份不完整状态不能伪装为 verified。
- DSH managed Job/Terminal 关闭优先走 owner API；外部操作必须重新校验 PID、creation identity、executable、user、protection/access，且只允许用户确认的单 PID。
- 不自动提权、不终止进程树、不修改 DSH core、不收集环境变量或原始 secrets。
- 用户手工验证使用的启动命令固定为：

```powershell
cd D:\project\deepseek-harness
pnpm dsh web --no-open --port 3080
```
