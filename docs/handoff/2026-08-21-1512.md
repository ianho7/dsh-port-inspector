## Problems Encountered and Decision Process

### Problem 1: No existing UI or Host RPC implementation

#### Investigation

The repository is a Windows MVP Bundle with runtime, scanner, lifecycle, Tool, and test modules, but no browser component, UI slot registration, or Host RPC gateway implementation. The accepted specification only required the Host/UI boundary to expose inventory and safe actions.

#### Solutions Considered

1. Add a concrete browser UI framework or invent a DSH Web slot contract.
   - Pros: could provide a visible table immediately.
   - Cons: would introduce an unsupported integration surface and dependencies not present in the repository; real DSH contract evidence is unavailable.

2. Implement a pure TypeScript Host/UI service and serializable RPC contract.
   - Pros: covers the acceptance behavior, is injectable and testable, keeps process ownership inside existing services, and leaves a future Web adapter possible.
   - Cons: does not render a browser UI by itself.

#### Final Decision

Use option 2. `runtimeInspector.host` is the trusted Host/UI boundary and `runtimeInspector.host.rpc` contains only serializable inventory and safe action methods.

#### Rationale and Future Implications

This is the smallest implementation that satisfies Ticket 07 without guessing at private DSH Web APIs. Ticket 08 or a later UI integration task should attach this contract to the actual supported DSH Host/RPC gateway if one is available.

### Problem 2: Preserving the existing single-service Bundle contract

#### Investigation

The first integration published a second `runtimeInspectorHost` service through `ctx.provide()`. Existing lifecycle tests require the Bundle to publish exactly one runtime inspector service, and a second publication would change the composition contract.

#### Final Decision

Remove the additional provider and attach the Host surface to the existing `runtimeInspector.host` property.

#### Rationale

The Host boundary remains available to the trusted UI consumer without changing Bundle publication count or lifecycle behavior. The model-facing Tool remains separately registered and read-only.

### Problem 3: Opening project directories without leaking or misusing redacted paths

#### Investigation

Project paths and workdirs cross output boundaries through redaction. A redacted path cannot safely be passed to an opener because it may not identify a real directory.

#### Final Decision

`openProjectDirectory` accepts only an opaque listener id, resolves the internal origin, refuses missing or redacted paths, and calls an injected host opener with the path only inside the trusted process. The RPC result never contains the raw path.

#### Rationale

This keeps directory opening useful for ordinary known workdirs while failing closed for sanitized or unavailable paths.

### Problem 4: Deterministic checks versus the Windows/DSH environment

#### Investigation

The bundled TypeScript compiler and Bun tests are available and pass. The npm shim cannot resolve `tsc`; `npm run typecheck` and `npm test` fail earlier because Volta cannot create its directory. The Stock DSH smoke is skipped without `DSH_REPO`, and the prior enabled attempt failed while copying native `koffi` with `EPERM`.

#### Final Decision

Record bundled build/test evidence as deterministic validation, retain the raw environment failures, and do not claim real DSH lifecycle acceptance.

## Key Decisions and Context

- Verified attribution requires PID plus canonical decimal FILETIME creation identity and a complete, unambiguous, cycle-free ancestry chain.
- Inferred attribution is diagnostic only and never grants managed-owner authority; it may still be offered to the external single-PID safety path when identity data is complete.
- Managed Job/Terminal shutdown uses DSH owner APIs and never escalates to PID or process-tree termination.
- External termination is a separate explicit same-user single-PID action with fresh PID, creation-time, executable, user, protection, and access checks; it never auto-elevates or recurses.
- The model-facing `port_list` Tool is read-only, bounded, redacted, Session-scoped, and contains no action capability.
- The trusted Host/UI surface is `runtimeInspector.host`; its RPC shape intentionally contains inventory, copy, directory-open, and action methods only.
- Host action dispatch always re-reads the selected listener before calling a lifecycle/action service and always performs a fresh scan afterward. Port release is reported only from a complete observed scan.
- Degraded compatibility and disposed lifecycle state remain visible but read-only; no stale origin data is used for verified claims.
- Commands, argv, executables, project paths, RPC fields, Tool output, and copied details must use the shared redaction and length-boundary helpers. Environment variables are never collected.
- The plugin is observational and does not own DSH processes. Unload removes its observers, Tool registration, and lifecycle state without terminating existing user processes.
