## Problems Encountered and Decision Process

### Problem: larger text would make the existing compact shell fight its content

#### Investigation

The review found a 13px root and scattered 9–11.5px declarations. The existing centered Modal was `1040px` wide, capped at `800px` high, with a fixed `54px` header and a `960px` responsive threshold. At a 1000px viewport the desktop toolbar and two-column minimums still applied, leaving too little room for larger labels, pills, and actions. Several internal flex rows also used non-wrapping content.

#### Solutions Considered

- Increase individual font declarations only. This would be quick, but would preserve inconsistent hierarchy and leave local overflow risks scattered across selectors.
- Increase the Modal width only. This would help the common desktop case, but would not solve compact viewports, wrapped status text, or non-wrapping row values.
- Use semantic typography tokens together with a wider capped shell, earlier responsive wrapping, and local overflow protections. This adds a small coordinated change but addresses the coupled geometry/type problem.

#### Final Decision

Use the coordinated token and responsive-shell approach: 14px base text, deliberate role tokens, `1120px` preferred width, `840px` capped height, `1040px` toolbar/compact-column threshold, `720px` stacked body, and `480px` narrow-screen fact/action rules.

#### Rationale

The changes preserve the DSH centered-dialog composition while giving typography enough measured space. Independent list/detail scrolling remains the final containment boundary, and the earlier compact mode prevents the known 961–1000px compression band.

#### Future Implications

Any future type increase should start from the semantic tokens and re-check the viewport matrix rather than adding selector-specific sizes. The testing guide and any preview generator should use the same geometry constants.

### Problem: technical values and localized labels could still clip inside otherwise contained rows

#### Investigation

Outer `overflow: hidden` and independent column scrolling did not protect non-wrapping inner flex content. Source/action pills had no dedicated shrinkable label, row addresses had no bounded recovery, and technical values in the detail subtitle/confirmation identity were not consistently marked.

#### Solutions Considered

- Allow every value to wrap. This protects content but makes compact rows noisy and unstable.
- Keep compact values bounded, preserve the complete value through a title/detail view, and allow intentionally multiline detail facts to wrap. This keeps scanning calm while preserving inspectability.

#### Final Decision

Wrap row top/meta flex lines; add shrinkable pill-label spans; bound compact addresses and preserve their full title; use `overflow-wrap:anywhere` for marked multiline detail facts; add technical monospace classes to list, detail, and confirmation values; allow header/detail/handling/action groups to wrap.

#### Rationale

The distinction between compact scan surfaces and detailed evidence surfaces is intentional. Ports and authority/action pills stay scannable, while full paths, commands, requests, and identifiers remain available in details or through accessible titles.

#### Future Implications

The next browser-backed fixture should include the exact long-content cases from ticket 05. Pay particular attention to long localized action labels and IPv6 addresses at 720px and 480px.

### Problem: the mobile width override did not fully supersede the desktop max-width

#### Investigation

Review of the computed-width model showed that setting `width: calc(100vw - 32px)` or `calc(100vw - 16px)` below the mobile breakpoints was insufficient while the base `max-width: calc(100vw - 48px)` remained active. The intended 720px and 480px panel widths therefore needed explicit matching `max-width` overrides.

#### Final Decision

Set both `width` and `max-width` in the `720px` and `480px` media rules. The expected widths are 688px at a 720px viewport and 464px at a 480px viewport.

#### Evidence

The responsive Web smoke matrix now asserts those widths and checks panel/body horizontal overflow at every viewport when the certified DSH Web environment is available.

### Problem: deterministic validation could not prove actual browser line breaking in this checkout

#### Investigation

The local package has React and TypeScript but no `jsdom`, `react-dom`, or Playwright dependency. The existing highest seam is the opt-in Stock DSH Web smoke, which requires an external certified checkout. Adding a new browser dependency or a fake DOM would increase scope and would not validate DSH composition.

#### Final Decision

Keep the existing deterministic Client seam for semantic/style contracts and strengthen the real Web smoke with computed geometry and overflow assertions. Defer long-content browser fixtures until the certified checkout is available.

#### Rationale

This preserves the repository’s existing test architecture and avoids treating source regexes as a substitute for real rendering. The limitation is explicit and is not reported as a passing live acceptance result.

### Problem: design preview drift risk

#### Investigation

The design preview contains a production-style CSS segment plus isolated prototype scaffolding. Editing both source and preview manually can cause dimensions or token values to diverge.

#### Final Decision

Reconcile the production segment with the current Browser source and add a normalized source/preview equality check that excludes only the known prototype scaffolding. Retain the static preview for its standalone design-review use.

#### Future Implications

A generator or single-source preview pipeline remains preferable, but it is not required to ship this presentation change.

## Key Decisions and Context

- The repository is a single DSH dual-face Bundle. Browser code must remain serializable-safe and must not import Windows scanner, process identity, Koffi, Job/Terminal, or termination primitives.
- The DSH locale service remains authoritative. The panel receives the resolved locale at the component boundary and uses `lang` for language-sensitive styling; it does not create a locale setting or take over document-language projection.
- The centered Modal remains an additive `shell.overlay` surface with the global Sidebar entry. It does not replace DSH Web’s Sidebar, Conversation, composer, or application root.
- Typography uses local system fonts only. The DSH font token is first choice, followed by Windows/macOS/system Latin and CJK fallbacks; no network font dependency is permitted.
- Technical data and prose have different treatment: technical values use monospace/tabular numerics where useful; Chinese/English explanatory copy uses the sans stack and larger paragraph line-height.
- The shell dimensions are measured targets, not new product semantics: `1120px` preferred width, `840px` preferred/capped height, `1040px` compact toolbar threshold, `720px` stacked body, and `480px` single-column narrow behavior.
- Local overflow handling is layered: reflow first, compact ellipsis with title recovery where appropriate, detail wrapping for marked multiline values, then independent column scrolling. No global page scroll was introduced.
- The implementation deliberately changed no Host DTO, Browser RPC payload, `port_list` schema, action authority, Process origin wording, attribution confidence, Lifecycle owner, or termination safety rule.
- The local spec and tickets are implementation records, not evidence that the environment-gated Stock DSH acceptance has run. The next engineer should treat the P2 validation gap as explicit work rather than infer success from the deterministic suite.
- Existing accepted architecture remains relevant: ADR-0004 governs the dual-face Bundle/Browser boundary, and ADR-0005 keeps DSH version metadata diagnostic while capabilities determine runtime behavior.
